# 68040 EmuTOS Variant with External MC68882

## Context

Create a 68LC040 (68040 without internal FPU) boot option in the validation firmware, using the external 50 MHz MC68882 FPGA hardware for FPU operations. This serves as an early testing ground for the full Merlin2 board, which will use a 68040-class CPU with the external MC68882.

The key insight: use `M68K_CPU_TYPE_68LC040` (no internal FPU) so F-line FPU instructions still trap to our existing `fline_illg_callback()` and get routed to the external hardware MC68882. The instruction encoding is identical between 68881/82 and 68040 FPU — both use the same F-line ($Fxxx) opword format.

## Files to Modify

| File | Change |
|------|--------|
| `musashi/m68kconf.h` | Enable `M68K_EMULATE_040` |
| `main.c` | Add boot menu option 3 for 68040 EmuTOS, set CPU type |
| `mfp_emu.c` | Update `CPU_CLOCK_HZ` to be variable (8 MHz vs higher for 040) |
| `rom_image.h` | Need a 68040-compatible EmuTOS ROM image (new file or replace) |

## Plan

### Step 1: Enable 68040 in Musashi

**File**: `musashi/m68kconf.h`

```c
#define M68K_EMULATE_040  M68K_OPT_ON   // was OFF
```

This compiles in 68040 instruction decoding (CINV, CPUSH, MOVE16, etc.). The F-line callback stays as-is — with `M68K_CPU_TYPE_68LC040`, FPU instructions still trap.

### Step 2: Add boot menu option

**File**: `main.c`

Add a third boot option:
```
  Select boot ROM:
    1 - EmuTOS 68000 (Atari ST desktop)
    2 - Merlin2 BIOS (monitor/assembler)
    3 - EmuTOS 68040 (Merlin2 test)
```

When option 3 is selected:
- `m68k_set_cpu_type(M68K_CPU_TYPE_68LC040)` — 68040 CPU without internal FPU
- Load 68040-compatible EmuTOS ROM
- Use same memory map, peripherals, floppy, blitter, etc.
- VBL/Timer C timing adjusted for higher emulated clock

### Step 3: EmuTOS 68040 ROM

Need a 68040-compatible EmuTOS build. Options:
- **EmuTOS 68040 build**: EmuTOS supports `make 256k` or `make aranym` which targets 68040. The `aranym` target uses 68040 CPU with PMMU.
- The ROM needs to be converted to `rom_image_040.h` (same format as existing `rom_image.h`)
- Load address stays at `$E00000` (or could be different for 68040 builds)

**Key consideration**: EmuTOS 68040 builds expect native FPU. With 68LC040, EmuTOS would install an FPSP (Floating Point Software Package) handler for the Line-F exception. But our Musashi callback intercepts BEFORE the 68K exception mechanism — Musashi calls `fline_illg_callback()` and if it returns 1, the instruction is "handled" without generating any exception. So EmuTOS never sees the FPU trap. This means:
- Our existing fline_handler.c handles all FPU instructions via external hardware
- EmuTOS's FPSP code never runs (which is fine — our hardware is faster)
- No conflict between FPSP and our hardware handler

### Step 4: Clock and timing adjustments

**File**: `mfp_emu.c`

The 68040 variant should emulate a faster clock. Options:
- 25 MHz (standard 68040)
- 33 MHz (common 68040 speed)
- 50 MHz (matching the external MC68882 clock)

Make `CPU_CLOCK_HZ` a variable set from main.c based on boot choice (8 MHz for 68000, 50 MHz for 68040). Adjust VBL counter:
- 68000: 8 MHz, 10000 cycles/tick, VBL every 12 ticks → ~66 Hz
- 68040: 50 MHz, 10000 cycles/tick, VBL every 83 ticks → ~60 Hz

### Step 5: Memory map considerations

The 68040 has a 32-bit address bus (4 GB) vs the 68000's 24-bit (16 MB). Our `EMU_RAM_SIZE` is 16 MB with `EMU_RAM_MASK` wrapping. For 68040:
- Keep the 16 MB emulated RAM for now (sufficient for EmuTOS)
- The `& EMU_RAM_MASK` wrapping still works — 68040 addresses above 16 MB just wrap
- I/O regions ($FF8xxx, $FFFAxx) are already in the 24-bit range so no change needed

### Step 6: Potential 68040-specific issues

1. **PMMU**: 68040 has MMU built in. EmuTOS 68040 may enable it. `M68K_EMULATE_PMMU` should stay OFF since we have flat memory. If EmuTOS tries to set up page tables, those writes would go to emu_ram harmlessly. PMMU translation in Musashi is disabled, so addresses pass through unchanged.

2. **Cache instructions**: CINV, CPUSH are 68040-specific. Musashi handles these internally. They're NOPs in our context since there's no real cache.

3. **MOVES instruction**: Used for supervisor/user space access. Musashi handles this for 68040.

4. **Stack frames**: 68040 uses different exception stack frame formats than 68000. Musashi handles this automatically based on CPU type. EmuTOS 68040 build expects 68040 frames.

## Verification

1. Build with `M68K_EMULATE_040 = ON` — check it compiles cleanly (Musashi 040 code may pull in softfloat; ensure no conflicts)
2. Boot option 1 (68000 EmuTOS) still works as before
3. Boot option 2 (Merlin2) still works
4. Boot option 3 (68040 EmuTOS):
   - EmuTOS version screen appears
   - FPU instructions route to external MC68882 (check UART debug for `[FPU]` messages)
   - Desktop loads (once floppy issues are resolved)
5. Run a simple FPU test program to verify 68040+MC68882 path works

## Resolved Decisions

- **Clock speed**: 50 MHz — matches the external MC68882 clock
- **CPU variants**: 040 only — just `M68K_EMULATE_040`, keep 010/020/030 OFF
- **EmuTOS ROM**: Build from source — include build instructions below

## EmuTOS 68040 Build Instructions

```bash
# Clone EmuTOS source
git clone https://github.com/emutos/emutos.git
cd emutos

# Build 68040 256K ROM (uses 68040 CPU target)
make 256k CPUFLAGS="-m68040"

# Or use the "aranym" target which targets 68040 with PMMU:
make aranym

# Output: emutos-aranym.img or etos256k.img

# Convert to C header for embedding:
# Extract from $E00000 base, same process as existing rom_image.h
xxd -i emutos-aranym.img > rom_image_040.h
# Edit to match naming convention (rom_image_040_data[], ROM_IMAGE_040_SIZE)
```

The `aranym` target produces a 68040-native EmuTOS with TT/Falcon hardware support. The `256k` target with `-m68040` flag produces a more generic 68040 build. Either should work with our memory map.

## Step 7: Add 68040-Only FPU Opcode Mappings

**File**: `validation/hello_world/src/fline_handler.c`

The 68040 added single/double-precision FPU instruction variants that the 68881/82 doesn't have. EmuTOS 68040 builds will use these. Our opcode mapping table needs entries for them.

Since the MC68882 hardware computes in 80-bit extended precision internally, these map directly to the same hardware operations as their extended-precision counterparts (results will be slightly more precise than a real 68040, which is acceptable).

### Opcode mapping additions

| 68040 opcode | Mnemonic | Maps to | Hardware op |
|---|---|---|---|
| `$40` | FSMOVE | `FPOP_MOVE` (0x00) | Move with single-precision rounding |
| `$44` | FDMOVE | `FPOP_MOVE` (0x00) | Move with double-precision rounding |
| `$41` | FSSQRT | `FPOP_SQRT` (0x04) | Sqrt with single-precision rounding |
| `$45` | FDSQRT | `FPOP_SQRT` (0x04) | Sqrt with double-precision rounding |
| `$58` | FSABS | `FPOP_ABS` (0x18) | Abs with single-precision rounding |
| `$5C` | FDABS | `FPOP_ABS` (0x18) | Abs with double-precision rounding |
| `$5A` | FSNEG | `FPOP_NEG` (0x1A) | Neg with single-precision rounding |
| `$5E` | FDNEG | `FPOP_NEG` (0x1A) | Neg with double-precision rounding |
| `$60` | FSDIV | `FPOP_DIV` (0x20) | Div with single-precision rounding |
| `$64` | FDDIV | `FPOP_DIV` (0x20) | Div with double-precision rounding |
| `$62` | FSADD | `FPOP_ADD` (0x22) | Add with single-precision rounding |
| `$66` | FDADD | `FPOP_ADD` (0x22) | Add with double-precision rounding |
| `$63` | FSMUL | `FPOP_MUL` (0x23) | Mul with single-precision rounding |
| `$67` | FDMUL | `FPOP_MUL` (0x23) | Mul with double-precision rounding |
| `$68` | FSSUB | `FPOP_SUB` (0x28) | Sub with single-precision rounding |
| `$6C` | FDSUB | `FPOP_SUB` (0x28) | Sub with double-precision rounding |

### Implementation

Add these to the `opcode_to_fpop[]` mapping array (or equivalent switch/if chain) in `fline_handler.c`. The dyadic operations (ADD, SUB, MUL, DIV) also need to be added to the `is_dyadic()` check.

**Note**: The single/double precision rounding is NOT enforced — the hardware returns extended precision. For correctness on a real 68040, the result should be rounded to single (32-bit) or double (64-bit) precision before storing back. For our testing purposes this is acceptable; if exact 68040 compatibility is needed later, add a post-operation rounding step to `fp_reg_set()` based on whether the opcode was an Fs/Fd variant.

## Step 8: Enable Color EmuTOS Graphics

**File**: `validation/hello_world/src/mfp_emu.c`

### Problem

EmuTOS boots in monochrome (resolution 2, 640x400) because MFP GPIP bit 7 reports a monochrome monitor. The color rendering code in `atari_video.c` already fully supports all three ST video modes with palette handling, but EmuTOS never selects a color mode.

### Root Cause

In `atari_mfp_init()`:
```c
amfp_regs[AMFP_GPIP] = 0x10;  /* bit 7 = 0 → mono monitor detected */
```

On the Atari ST, GPIP bit 7:
- **0** = monochrome monitor connected (SM124) → EmuTOS forces resolution 2
- **1** = color monitor connected (SC1224) → EmuTOS uses resolution 0 (low, 16 colors)

### Fix

Change the GPIP init to report a color monitor:
```c
amfp_regs[AMFP_GPIP] = 0x90;  /* bit 7 = 1 (color monitor), bit 4 = 1 (ACIA idle) */
```

Also ensure the GPIP read handler preserves bit 7:
```c
case AMFP_GPIP: {
    uint8_t gpip = amfp_regs[AMFP_GPIP];
    /* Bit 7: Monitor type (1=color, 0=mono) — static, from init */
    /* Bit 5: FDC interrupt ... */
    /* Bit 3: Blitter done ... */
    ...
}
```

Bit 7 is already preserved since the GPIP read handler only modifies bits 3, 4, and 5.

### What already works (no changes needed)

- **`atari_video.c`**: `render_low()` decodes 4-bitplane ST Low (320x200, 16 colors) with 4x3 scaling to 1280x600
- **`atari_video.c`**: `render_med()` decodes 2-bitplane ST Medium (640x200, 4 colors) with 2x3 scaling
- **Palette**: `$FF8240-$FF825F` writes expand 3-bit ST RGB to 8-bit ABGR via `(c << 5) | (c << 2) | (c >> 1)`
- **Display pipeline**: ABGR pixel buffer → DPDMA → DisplayPort 1280x720@60

### Expected Result

EmuTOS boots in ST Low (320x200, 16 colors). The GEM desktop appears with the classic Atari color scheme — green desktop background, white window title bars, colored icons. The blitter draws in color using the palette-indexed bitplane data.

## Step 9: FPU Detection for 68000 — Cookie Jar Patching

**File**: `validation/hello_world/src/main.c`

### Problem

The validation PCB uses a real 68000 CPU. Our F-line callback makes FPU instructions work transparently via the external MC68882, but EmuTOS's 68000 build has no FPU detection code — it never tries F-line FPU instructions because a real 68000 can't have a coprocessor. So `_FPU` cookie = 0 (no FPU) even though the hardware MC68882 is present and functional.

### Approach

Patch the cookie jar in emulated RAM after EmuTOS has initialized it. The Atari ST cookie jar works as follows:

- System variable at `$5A0` (`_p_cookies`) = 32-bit pointer to cookie jar array
- Cookie jar = array of 8-byte entries: `[4-byte ID][4-byte value]`
- Terminated by a null entry: `[0x00000000][max_entries]`

Standard cookie values:
- `_FPU` (`0x5F465055`): FPU type
  - 0 = no FPU
  - 2 = 68881
  - 4 = 68882
  - 6 = 68040 internal FPU
  - 8 = 68060 internal FPU

### Implementation

Add a one-shot cookie jar patch in the main emulation loop, triggered after EmuTOS has booted (e.g. after the first VBL or when the resolution register is written — indicating EmuTOS init is past the cookie jar setup):

```c
static int cookies_patched = 0;

/* After EmuTOS has initialized (resolution set = init complete) */
if (!cookies_patched && atari_vid_active()) {
    cookies_patched = 1;

    /* Read _p_cookies pointer from $5A0 */
    uint32_t jar_ptr = m68k_read_memory_32(0x5A0);
    if (jar_ptr != 0 && jar_ptr < EMU_RAM_SIZE - 64) {
        /* Walk jar to find terminator (ID == 0) */
        uint32_t p = jar_ptr;
        uint32_t max_cookies = 0;
        int count = 0;
        while (count < 32) {  /* safety limit */
            uint32_t id = m68k_read_memory_32(p);
            if (id == 0) {
                max_cookies = m68k_read_memory_32(p + 4);
                break;
            }
            p += 8;
            count++;
        }

        if (max_cookies > 0 && count + 1 < (int)max_cookies) {
            /* Insert _FPU cookie at current terminator position */
            m68k_write_memory_32(p, 0x5F465055);  /* '_FPU' */
            m68k_write_memory_32(p + 4, 4);        /* 68882 */
            /* Write new terminator after it */
            m68k_write_memory_32(p + 8, 0);
            m68k_write_memory_32(p + 12, max_cookies);
            xil_printf("[ROM] Cookie jar patched: _FPU=4 (MC68882)\r\n");
        }
    }
}
```

### Why this is correct

This is not a workaround — it's the equivalent of what real hardware does. On a real 68000 board with a memory-mapped 68882 (like the validation PCB), the BIOS/ROM would detect the FPU hardware and set the cookie. Since our BIOS is EmuTOS (which doesn't know about our particular hardware interface), we do the detection on the ARM side and inject the cookie. The cookie jar is the standard Atari mechanism for hardware enumeration — we're using it as designed.
